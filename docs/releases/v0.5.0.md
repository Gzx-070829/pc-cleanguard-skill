# PC CleanGuard v0.5.0 — Governance Re-foundation

## Why we changed

The final v0.4 comparison scored Bare Codex 87.3 and Codex + PC CleanGuard 89.5,
a delta of only +2.2. That did not prove enough independent value for continued
development of a large Cleaner/PUP/Persistence Skill. The old route remains
`FEATURE_FROZEN`; its evidence and negative conclusion are preserved.

## What was removed from the core

- Cleaner-first positioning
- PUP-first positioning
- Reputation-driven product strategy
- Persistence graph as product center
- competition with general Agent intelligence

## What remains

- deterministic L0-L5 Policy
- decision-bound Consent
- execution-time Preconditions and TOCTOU defense
- Rollback Contract validation
- hash-chained Audit receipts
- Windows protected paths and Developer Guard
- external Executor boundary

## What became legacy

Windows collection/reporting, cleanup preview and bounded L1 execution,
quarantine/restore, PUP/Reputation/Behavior/Evidence flows, Persistence Graph,
demos, trials, and the broad v0.1-v0.4 Skill action interface remain for
compatibility and reproducibility. They cannot authorize the v0.5 Guard.

## Highlights

- Thin `pc_cleanguard.guard` package and root `Guard` API
- Three dispositions and stable action/decision/consent/rollback/execution models
- Monotonic restriction-only intelligence signals
- Consent anti-spoofing and scope/fingerprint/target/effect binding
- Target hash/size/mtime/type/path/reparse/protection revalidation
- ActionBundle maximum-restriction aggregation and rollback order
- Exactly eight Agent-boundary schemas and five primary Skill actions
- Guard-first CLI with stdin JSON mode and documented exit codes
- 21-scenario offline Governance Acceptance Benchmark

## Limitations

PC CleanGuard is not an OS sandbox. It is not kernel enforcement, EDR, antivirus,
or a generic executor.

An Agent that can bypass the integration and directly call Windows APIs can
bypass PC CleanGuard. Enforcement requires the integrating Agent host to route
relevant actions through the Guard and authenticate Consent through a trusted
host/UI.

v0.5.0 adds no real L3 uninstall executor and no real L4 registry/service/startup/
scheduled-task/browser executor. Guard authorization is a contract for an
external, separately governed executor—not an operation performed by the Guard.
