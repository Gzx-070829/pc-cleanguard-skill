# v0.5.0 Existing Architecture Review

## Root cause

The repository accumulated capable but broad modules for cleanup previews and
execution, quarantine, Windows collection, PUP evidence, reputation, persistence
graphs, reports, demos, and AI-facing actions. The final v0.4 A/B result (+2.2)
showed that this breadth did not create enough independent product value. The
stable value was not additional intelligence; it was the deterministic safety
boundary around a proposed system action.

## Existing components and disposition

| Existing area | Useful property | v0.5 disposition |
| --- | --- | --- |
| `core/policy_engine.py` | Pure, non-executing decisions and hard protection | Legacy compatibility; concepts re-expressed in the new contract |
| `core/models.py` | Stable v0.1-v0.4 report models | Preserve imports; do not overload with v0.5 contracts |
| `protection/developer_guard.py` | Pure path-component protection | Reuse as a narrow utility |
| cleanup executor | Controlled L1 compatibility behavior | Keep outside Guard; never import from Guard Core |
| quarantine/restore | Reversible legacy executor | Keep outside Guard; may consume future contracts, never authorize them |
| audit logger | Append-only dry-run JSONL | Preserve; new Guard gets a separate canonical hash chain |
| PUP/Reputation/Behavior | Review and explanation signals | Optional intelligence only |
| persistence graph | Rich relationship intelligence | Optional intelligence only; retain bundle-ordering lesson |
| Windows collectors | Read-only metadata | Compatibility adapters; never an authorization source |
| Skill actions and CLI | Existing integration surface | Keep commands, label Legacy/Compatibility, add Guard-first surface |

## Problems that the re-foundation must correct

1. Old classifications and plans are domain-specific and are not a stable action
   authorization contract.
2. A boolean such as `user_confirmed` has no authenticated decision, target,
   effect, scope, expiry, or fingerprint binding.
3. Preview-time facts can become stale before execution (TOCTOU).
4. Existing JSONL audit records are append-only but not tamper-evident.
5. Old broad Skill actions expose product subsystems instead of a thin governance
   boundary.
6. Intelligence inputs need an explicit one-way, restriction-only contract.

## Reuse decision

The new package may depend on Python's standard library and the already-general
Developer Guard utility. It must not import cleanup executors, quarantine
managers, PUP, reputation, persistence intelligence, Windows collector execution,
AI providers, or network libraries. This preserves a clean dependency direction:

```text
optional intelligence / compatibility executors
                    -> structured inputs or contract consumers
                    -> Guard public boundary

Guard Core -X-> old cleaner / PUP / reputation / persistence / executor
```

## Complexity gate

The core is deliberately limited to approximately eleven Python modules, eight
JSON schemas, five Skill actions, and four principal public operations. No new
manager hierarchy, plugin runtime, policy DSL, database, network client, LLM
provider, shell runner, or generalized cross-platform framework is justified.

## Architecture self-check

- This is not a new Cleaner: the core cannot scan or delete.
- This is not a new PUP system: intelligence cannot issue authorization.
- This does not duplicate quarantine: rollback is a validated contract, not an
  implementation.
- Compatibility stays outside the new dependency graph.
- Windows remains the validated operating domain; the data contracts avoid
  gratuitous cross-platform abstraction.
