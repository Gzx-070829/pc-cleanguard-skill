# v0.5.0 Migration Map

## Product surface

| v0.4 surface | v0.5 status | Migration path |
| --- | --- | --- |
| Cleaner-first README | Frozen | Guard-first README; old demos linked as legacy |
| Cleanup classifications | Compatibility | Convert proposed effects into `ActionRequest`; policy decides level |
| Boolean confirmation flags | Compatibility only | Trusted host issues a bound, expiring `ConsentGrant` |
| Cleanup/quarantine execution | External/legacy executor | Consume an `ExecutionContract`; never imported by Guard |
| Dry-run audit JSONL | Compatibility | New Guard audit uses canonical hash chaining |
| PUP/Reputation evidence | Optional intelligence | Adapt to `RiskSignal`/evidence reference; restriction-only |
| Persistence graph | Optional intelligence | Translate concrete mutations into an `ActionBundle` |
| Read-only Windows collectors | Compatibility | Supply target facts; never issue a decision |
| Broad Skill action set | Legacy/Compatibility | Five Guard actions become the primary Agent contract |
| Existing CLI commands | Legacy/Compatibility | Continue working with stderr warning; `guard` is primary |

## Dependency boundary

```text
Host / Agent
  -> pc_cleanguard.guard public API
       -> models / normalize / policy
       -> consent / preconditions / rollback
       -> audit / batch
       -> Developer Guard utility (path protection only)

Legacy intelligence -> RiskSignal or EvidenceReference -> Guard input
Legacy executor <- ExecutionContract <- Guard output
```

The arrows are intentionally one-way. Legacy intelligence cannot import Guard
internals to force `ALLOW`, and Guard Core cannot import legacy engines.

## Compatibility promise

v0.1-v0.4 modules, examples, final A/B documents, real-machine validation, and
historical CLI workflows remain in place. They are not silently rewritten to
claim v0.5 success. Compatibility is best-effort and is clearly marked outside
the v0.5 product core.

## Adoption sequence

1. Integrating host constructs a strict `ActionRequest` and trusted
   `GuardContext`.
2. Host calls `evaluate` and presents requirements to the user.
3. Trusted UI authenticates consent and issues a narrowly bound grant.
4. Host re-observes the target and supplies a current context.
5. Host supplies the required rollback contract or plan.
6. Guard issues an expiring execution contract.
7. An external executor performs only the authorized effect and reports the
   result.
8. Host records and verifies the audit chain.

No existing Cleaner command is automatically routed through this sequence in
v0.5.0; doing so without a trusted-host design would create a misleading security
claim.
