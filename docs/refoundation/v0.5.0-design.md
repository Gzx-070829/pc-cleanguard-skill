# v0.5.0 Guard Design

## Core flow

```text
ActionRequest
  -> deterministic Policy Gate
  -> Consent + Preconditions + Rollback validation
  -> ExecutionContract
  -> external ExecutorProtocol implementation
  -> execution result + hash-chained AuditEvent
```

The Guard is a contract authority, not an executor and not an OS security
boundary.

## Stable data boundary

- `ActionRequest` describes action type, targets, parameters, requested effect,
  timestamp, agent identity/reason, evidence references, and dry-run state.
- `ActionTarget` separates structured identity, path, metadata, and observed facts.
- `GuardContext` carries trusted scope and current facts plus untrusted risk
  signals. `agent_reason` never enters policy matching or fingerprints.
- `GuardDecision` has only `ALLOW`, `REQUIRE`, or `BLOCK`; granular gates are
  requirements.
- `ConsentGrant`, `RollbackContract`, and `ExecutionContract` bind the exact
  decision, action fingerprint, targets, effect, scope, and expiry.

All serialized models use strict field validation, canonical dictionaries, UTC
timestamps, and SHA-256 fingerprints. Identical policy inputs produce identical
decision fingerprints; operational IDs and display timestamps are derived
deterministically for decisions rather than generated randomly.

## Policy model

| Level | Meaning | Minimum result |
| --- | --- | --- |
| L0 | Read-only metadata/report/preview/explain | `ALLOW`; audit record |
| L1 | Narrow low-risk mutation | confirmation, target revalidation, audit |
| L2 | Reversible filesystem mutation | L1 + rollback contract + postcondition |
| L3 | Official uninstall contract | confirmation, rollback plan, revalidation, audit, postcondition |
| L4 | High-risk system mutation | explicit high-risk confirmation, backup, rollback, revalidation, audit, postcondition |
| L5 | Forbidden action or protected target | `BLOCK`; never authorizable |

Hard-block rules cover Windows/System32, boot/recovery, credential/password
stores, security cores, developer assets, wildcard or unbounded mutations,
policy-bypass requests, and evidence/reputation-driven deletion. Protected facts
are structured context—not natural-language claims.

## Monotonic safety

Untrusted `RiskSignal` values are ordered by restriction. Merging signals may add
requirements, raise the risk level, or block; it cannot remove a requirement,
lower risk, turn `REQUIRE` into `ALLOW`, or turn `BLOCK` into anything else.

## Consent boundary

Consent validation checks expiry, decision ID, action fingerprint, exact targets,
effect, scope, and confirmation strength. A field inside an Agent request is not a
grant. Authenticity of `confirmation_source` belongs to the trusted integrating
host/UI; PC CleanGuard validates the bound facts it receives and does not
pretend to provide kernel identity.

## Preconditions and TOCTOU

`prepare_execution` validates current facts against the decision snapshot:
existence, type, hash, size, modification time, allowed path scope, reparse-point
status, protected status, backup presence, and rollback readiness. A changed
target causes rejection and requires a fresh evaluation.

## Rollback and execution

L2-L4 actions require a rollback contract (L3 may use a documented rollback
plan). The Guard validates completeness and binding but performs no rollback.
Only after policy, consent, preconditions, and rollback gates succeed may the
Guard issue a short-lived `ExecutionContract`. Executors receive a protocol and
contract; there is no generic subprocess or PowerShell implementation.

## Audit

Every event is canonical JSON whose SHA-256 covers its content and the previous
event hash. Verification checks record structure, hashes, and link order. This is
a local tamper-evident log, not a blockchain or a semantic event-sequence proof.

## Batch

Every child request is evaluated independently. Aggregate disposition and risk
are the maximum restriction across children. Any block prevents bundle execution.
The result preserves declared dependency order and computes reverse rollback
order for actions that could have completed before a later failure.

## Public surface

Python:

```python
from pc_cleanguard import ActionRequest, Guard, GuardContext

decision = Guard().evaluate(request, context)
contract = Guard().prepare_execution(
    decision=decision,
    consent=consent,
    rollback=rollback,
    current_context=current_context,
)
```

Principal operations are `evaluate`, `prepare_execution`,
`record_execution_result`, and `verify_audit`. Core Skill actions mirror these
operations plus bundle evaluation. CLI machine mode prints JSON only to stdout;
diagnostics and compatibility warnings go to stderr.

## Enforcement limitation

PC CleanGuard is not a sandbox, kernel enforcement mechanism, or EDR. An Agent
that can bypass the integration and call Windows APIs directly can bypass the
Guard. Enforcement requires the integrating host to route relevant actions
through this boundary.
